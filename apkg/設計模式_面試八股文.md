# 設計模式 面試八股文

> 整理自網路常見的設計模式面試題，涵蓋 SOLID 原則、23 種 GoF 模式、常見模式比較、實務應用場景。

---

## 一、設計原則

### Q1. SOLID 五大原則？
- **S — Single Responsibility**：一個類別只應有一個變更原因。
- **O — Open/Closed**：對擴展開放，對修改封閉，透過抽象與多型擴充。
- **L — Liskov Substitution**：子類別可替換父類別不破壞行為。
- **I — Interface Segregation**：寧可多個小介面，避免胖介面。
- **D — Dependency Inversion**：高層模組依賴抽象，不依賴具體；具體實作依賴抽象。

### Q2. 何謂 DRY、KISS、YAGNI？
- **DRY (Don't Repeat Yourself)**：避免知識重複。
- **KISS (Keep It Simple, Stupid)**：保持簡單，可讀勝過炫技。
- **YAGNI (You Aren't Gonna Need It)**：不要實作目前不需要的功能。

### Q3. 迪米特法則 (Law of Demeter)？
「最少知識原則」：物件只與直接朋友交談，不要呼叫朋友的朋友。減少耦合。違反例：`a.getB().getC().doSomething()`。

### Q4. 組合優於繼承 (Composition over Inheritance) 為什麼？
- 繼承是強耦合、編譯期固定行為，且容易產生類別爆炸。
- 組合在執行期可動態替換策略，並避免父類變更牽動所有子類別。
- 設計模式中的策略、裝飾、橋接都體現此原則。

### Q5. GoF 23 種設計模式怎麼分類？
- **創建型 (Creational)**：單例、工廠方法、抽象工廠、建造者、原型。
- **結構型 (Structural)**：適配器、橋接、組合、裝飾、外觀、享元、代理。
- **行為型 (Behavioral)**：責任鏈、命令、解釋器、迭代器、中介者、備忘錄、觀察者、狀態、策略、模板方法、訪問者。

## 二、創建型模式

### Q6. 單例模式 (Singleton) 有哪些實作？
- 餓漢式：類別載入即建立。
- 懶漢式：第一次取用時建立，需處理執行緒安全。
- Double-Checked Locking：volatile + 兩層檢查。
- 靜態內部類別 (Holder pattern)：依賴 JVM class loader 的執行緒安全。
- 列舉 (Enum)：Effective Java 推薦，天然防序列化破壞與反射攻擊。
- Python：模組層級變數 / `__new__` / metaclass。

### Q7. 單例模式有哪些缺點？
- 隱藏相依，難以替換為 mock，影響單元測試。
- 全域可變狀態。
- 多 ClassLoader / 多 JVM 環境下不再「唯一」。
- 容易濫用為「全域變數」反模式。

### Q8. 工廠方法 (Factory Method) 與抽象工廠 (Abstract Factory) 差別？
- **工廠方法**：定義建立物件的介面，由子類別決定具體型別。一個工廠對應一個產品族中的單一產品。
- **抽象工廠**：建立「一整個產品族」的多種相關物件（如 Mac UI 元件 vs Windows UI 元件），通常包含多個工廠方法。

### Q9. 簡單工廠（靜態工廠）算 GoF 模式嗎？
不算，GoF 沒有列入。常見如 `valueOf`、`Integer.parseInt`。優點是簡化建立邏輯，缺點是新增類型需修改工廠（違反 OCP）。

### Q10. 建造者 (Builder) 模式適用場景？
- 物件參數眾多、有可選欄位（避免「望遠鏡建構子」）。
- 物件需逐步組裝、不可變。
- 與工廠的差別：建造者強調「組裝過程」，工廠強調「產品選擇」。
```java
Pizza p = new Pizza.Builder().size(12).cheese(true).pepperoni(true).build();
```

### Q11. 原型 (Prototype) 模式核心？
透過複製既有物件而非 new 出新物件，常用於建立成本高、或需要保留執行期狀態的物件。實作：`clone()` 方法、序列化拷貝、Python `copy.deepcopy`。

### Q12. 物件池 (Object Pool) 屬於哪一類？
不在 GoF 23 種內，但屬創建型衍生。用於昂貴資源（DB 連線、執行緒）的循環復用，需處理借出/歸還、最大數、超時等。

## 三、結構型模式

### Q13. 適配器 (Adapter) 模式？
將不相容的介面轉換為客戶端期望的介面。
- 物件適配器：透過組合包裝被適配對象。
- 類別適配器：多重繼承（Java 用介面）。
常見例：`InputStreamReader`（byte stream → char stream）、整合第三方 SDK。

### Q14. 橋接 (Bridge) 模式怎麼解決什麼？
將「抽象」與「實作」沿兩條維度分離，避免 m × n 類別爆炸。例如 Shape × Renderer，圓形/方形 × SVG/Canvas/PDF。

### Q15. 組合 (Composite) 模式應用？
將「整體與部分」用同一介面表達，客戶端不必區分葉節點與容器。例：檔案系統（File / Directory）、UI 元件樹、Menu。

### Q16. 裝飾者 (Decorator) 模式？
動態為物件加功能，不修改原有類別。Java IO 系列為經典：`new BufferedReader(new InputStreamReader(System.in))`。
- 與繼承差別：裝飾者可疊加組合、運行期決定。

### Q17. 外觀 (Facade) 模式？
為複雜子系統提供統一入口介面，降低外部依賴。例：SLF4J 對多個 logger 實作；Spring 的 `JdbcTemplate` 包裝 JDBC API。

### Q18. 享元 (Flyweight) 模式？
共享大量細粒度物件以節省記憶體，將「內部狀態」共享、「外部狀態」由客戶端傳入。例：`Integer.valueOf` 緩存 -128~127、字串常量池、Java `Boolean.TRUE`。

### Q19. 代理 (Proxy) 模式有哪些變體？
- 遠端代理 (Remote)：RPC stub。
- 虛擬代理 (Virtual)：延遲載入大物件。
- 保護代理 (Protection)：權限檢查。
- 智能引用 (Smart Reference)：引用計數、Lazy Init。
Spring AOP、Hibernate 延遲載入皆屬代理。

### Q20. Decorator、Proxy、Adapter 怎麼分？
| 模式 | 目的 | 介面是否相同 |
|------|------|-------------|
| Adapter | 轉換不相容介面 | 不同 → 相同 |
| Decorator | 動態加功能 | 相同（且可疊加） |
| Proxy | 控制存取 | 相同（多半不可疊加） |

## 四、行為型模式

### Q21. 責任鏈 (Chain of Responsibility) 模式？
將請求沿著處理者鏈傳遞，每個處理者決定處理或轉交下一棒。例：Servlet Filter、Spring Security FilterChain、OkHttp Interceptor、Netty Pipeline。

### Q22. 命令 (Command) 模式？
把「請求」封裝為物件，可排程、紀錄、回放、撤銷。例：GUI 按鈕事件、Redo/Undo、訊息隊列任務。

### Q23. 解釋器 (Interpreter) 模式何時用？
為小型 DSL 定義語法樹並逐節點解釋執行。實務上用得不多，較常被 ANTLR / Parser Combinator / 規則引擎 取代。

### Q24. 迭代器 (Iterator) 模式？
封裝集合走訪邏輯，客戶端不需知道內部結構。Java `Iterator/Iterable`、Python `__iter__/__next__`、C# `IEnumerator`。

### Q25. 中介者 (Mediator) 模式？
多對多協作改為「多對一」：所有物件透過中介者通訊。例：聊天室、UI Controller。減少耦合但中介者本身可能變胖。

### Q26. 備忘錄 (Memento) 模式？
在不破壞封裝下擷取物件內部狀態並可還原。常見於編輯器 Undo、遊戲存檔。

### Q27. 觀察者 (Observer) 模式？
一對多依賴，主體狀態改變時自動通知所有觀察者。Java `PropertyChangeListener`、JS DOM Event、Vue/React 響應式、訊息系統。

### Q28. 觀察者與 Pub/Sub 差別？
- Observer：主體與觀察者相互知道（同一程序內）。
- Pub/Sub：透過 broker 解耦，發送與訂閱方互不知對方存在，常跨程序/網路。

### Q29. 狀態 (State) 模式？
物件行為依「狀態」改變；將狀態抽出為獨立類別，避免巨大 if/switch。例：訂單流程、TCP 連線狀態、工作流引擎。

### Q30. 策略 (Strategy) 模式？
封裝可互換的演算法，客戶端在執行期選擇。例：排序比較器 (Comparator)、支付方式、日誌格式化。

### Q31. 狀態與策略模式怎麼分？
- 策略：客戶端「主動」選演算法；策略間獨立。
- 狀態：物件「自身」根據內部狀態自動切換行為；狀態之間有轉換關係。

### Q32. 模板方法 (Template Method) 模式？
父類定義演算法骨架，將可變步驟交給子類實作，搭配 hook 方法。例：Spring `JdbcTemplate.execute`、Servlet `service` → `doGet/doPost`。

### Q33. 訪問者 (Visitor) 模式？
將「操作」與「資料結構」分離，新增操作不需改資料類別，但新增資料類別需改所有 Visitor。常見於 AST 走訪（編譯器、ESLint）。

## 五、模式比較與綜合

### Q34. 工廠方法 vs 模板方法？
- 工廠方法：「建立物件」的抽象，回傳產品。
- 模板方法：「演算法骨架」的抽象，由子類補上步驟。
- 工廠方法常被 GoF 視為模板方法的一種特例。

### Q35. 策略 vs 命令？
- 策略：替換「怎麼做」的演算法（多個演算法、結果意義相同）。
- 命令：把「做什麼」物件化，可記錄、排程、撤銷。

### Q36. 觀察者 vs 中介者？
- 觀察者：一對多通知；主體不關心觀察者具體是誰。
- 中介者：多對多協調集中於中介者，物件不互相訂閱。

### Q37. 裝飾者 vs 責任鏈？
- 裝飾者：每層都呼叫下一層，目的是「附加行為」，仍會執行核心。
- 責任鏈：每個節點可選擇處理或轉交，目的是「找到能處理者」。

### Q38. 代理 vs 裝飾者？
- 代理控制存取（權限、延遲、遠端），通常一層。
- 裝飾者擴充功能，可多層疊加。
- 兩者實作上常極為相似，從「意圖」區分。

### Q39. Builder vs Factory？
- Factory：你告訴它「要什麼產品」，一次給你完整物件。
- Builder：你逐步告訴它「要怎麼組裝」，最後 build 出物件。

### Q40. 享元 vs 單例？
- 單例：全程序唯一一個。
- 享元：多個共享小物件池，按 key 取出共用實例（Integer 緩存）。

## 六、實務應用情境

### Q41. Spring 用了哪些設計模式？
- 工廠：BeanFactory、ApplicationContext。
- 單例：預設 bean 作用域。
- 代理：AOP（JDK Proxy / CGLIB）。
- 模板方法：JdbcTemplate、RestTemplate。
- 觀察者：ApplicationEvent。
- 策略：Resource、Spring Security 認證流程。
- 責任鏈：HandlerInterceptor、FilterChain。

### Q42. JDK 中有哪些常見設計模式？
- 工廠：`Calendar.getInstance`、`LoggerFactory`。
- 單例：`Runtime.getRuntime`。
- 適配器：`Arrays.asList`、`InputStreamReader`。
- 裝飾者：Java IO 體系。
- 享元：`Integer.valueOf`、字串常量池。
- 觀察者：`PropertyChangeListener`、`EventListener`。
- 命令：`Runnable`、`Callable`。
- 模板方法：`AbstractList`、`HttpServlet.service`。
- 迭代器：`Iterator`。

### Q43. MVC、MVP、MVVM 差別？
- **MVC**：View 主動呼叫 Controller，Controller 操作 Model；常見 Web 後端。
- **MVP**：View 透過介面呼叫 Presenter，Presenter 不直接持有具體 View，便於測試。
- **MVVM**：ViewModel 暴露可觀察狀態，View 透過資料綁定自動更新；Vue / Angular / WPF。

### Q44. DDD 與設計模式關係？
DDD 屬戰略/戰術設計，包含 Aggregate、Repository、Domain Service、Value Object。內部仍會用工廠、策略、規格 (Specification) 等模式落地。

### Q45. 如何避免設計模式濫用？
- 模式是「描述既有解法」，不是「目標」。
- 先看需求是否變動方向明確，再決定是否抽象。
- 優先 KISS/YAGNI；當第三次出現相似需求再重構成模式（Rule of Three）。
- 警惕「框架化早期業務」帶來的維護負擔。

### Q46. 反模式 (Anti-Pattern) 有哪些常見？
- God Object：一個類別承擔過多責任。
- Spaghetti Code：流程混亂、無清晰分層。
- Magic Number / String：硬編碼。
- Singleton 濫用：變相全域變數。
- 貧血模型：實體只剩 getter/setter，業務邏輯散落 Service。
- Premature Optimization：過早優化。

### Q47. 規格模式 (Specification) 是什麼？
GoF 之外，DDD 衍生的。把業務規則封裝為 boolean predicate，可組合 (`and`、`or`、`not`)。例：`new ActiveUser().and(new HasOrderInLast30Days())`，便於重用與測試。

### Q48. CQRS 與設計模式關係？
Command Query Responsibility Segregation：命令端與查詢端分離，常與事件溯源 (Event Sourcing) 搭配。內部會用命令、觀察者、工廠等模式組合。

### Q49. 依賴注入 (DI) 與依賴反轉 (DIP) 差別？
- DIP：原則層級（高層依賴抽象）。
- DI：實作技巧，把相依由「自己 new」改為「外部注入」。
- IoC 容器（Spring、Guice）是 DI 的工程化實作。

### Q50. 重構時哪些模式最常被引入？
- 替換大量 if/else → 策略 / 狀態。
- 構造函式爆炸 → Builder。
- 條件型物件建立 → 工廠 / 抽象工廠。
- 共通流程不同細節 → 模板方法。
- 跨層通訊複雜 → 中介者 / 觀察者 / 事件匯流排。
- 介面不相容 → 適配器。
- 想加功能但不能改原碼 → 裝飾者 / 代理。
